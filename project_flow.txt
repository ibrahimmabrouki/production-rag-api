             3. TOKEN BUDGET — SECOND / ATOMIC LAYER
════════════════════════════════════════════════════════════════════

Why another check?

The first check is useful, but it is NOT enough for concurrency.

Example:

                Browser Tab A
                      │
                      ▼
                  Request A
                      │
                      ▼
                FastAPI Worker 1
                      
                Browser Tab B
                      │
                      ▼
                  Request B
                      │
                      ▼
                FastAPI Worker 2


Both requests may belong to:

thread_id = "chat-123"


Worker 1                            Worker 2
   │                                  │
   ▼                                  ▼
read usage = 49                    read usage = 49
   │                                  │
   ▼                                  ▼
Layer 1 passes                    Layer 1 passes

If limit = 50, both workers could believe another request is allowed.

                    ↓
                RACE CONDITION


Therefore:

ChatUsageRepository.reserve_request(...)
                     │
                     ▼
              Redis Lua Script
                     │
                     ▼

════════════════════════════════════════════════════════════════════
                   LUA EXECUTES INSIDE REDIS
════════════════════════════════════════════════════════════════════

Redis atomically performs:

        READ CURRENT REDIS STATE
                  │
                  ▼
        total_input_tokens
        total_output_tokens
        total_requests
                  │
                  ▼
       Check request limit
                  │
                  ▼
       Check projected token limit
                  │
          ┌───────┴────────┐
          │                │
       REJECT            ALLOW
          │                │
          │                ▼
          │        HINCRBY input tokens
          │                │
          │                ▼
          │        HINCRBY requests
          │                │
          └─────────┬──────┘
                    │
                    ▼
        Lua operation completes


The entire:

READ → CHECK → UPDATE

is one atomic Redis operation.

No other FastAPI worker can modify the relevant Redis state
in the middle of this Lua execution.


Example:

Worker 1 Lua                    Worker 2 Lua

current requests = 49
       │
       ▼
allowed
       │
       ▼
requests = 50
       │
       ▼
Lua finishes
                                  │
                                  ▼
                           current requests = 50
                                  │
                                  ▼
                               REJECT


This is what prevents concurrent requests using the same
thread_id from exceeding the configured limits.

Both cache implementations use the shared Redis infrastructure.

Exact cache:
cleaned query → exact cache key → Redis

Semantic cache:
cleaned query
      ↓
embedding
      ↓
Redis vector search
      ↓
similar cached query/response


If the cache lookup itself fails:

Redis / embedding / semantic search failure
                  │
                  ▼
             exception caught
                  │
                  ▼
       treat it as CACHE MISS
                  │
                  ▼
             call Agent


A cache failure therefore does NOT make the chat unavailable.
